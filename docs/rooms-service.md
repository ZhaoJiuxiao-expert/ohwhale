# Local rooms service

`RoomService` is independent from friends, groups, media, plugins, and private conversations. The desktop constructor requires `{dir, store, harness, encrypt, decrypt, onEvent?}`. Android passes `encryptedFileSystem: true` only when using the application's encrypted native filesystem shim. An unencrypted filesystem must never use that bypass.

`ROOMS_METHODS` maps the eight `rooms*` bridge names to service methods. Methods accept named object arguments. `overview()` returns `{rooms, templates, agents}`; agent configuration readiness is checked by Harness selection without requesting a model. `create({templateId, agentIds?, name?})` accepts `dorm`, `travel`, or `game`, and exactly three existing characters, defaulting to `deepseek`, `qwen`, and `kimi`. It returns `{room}` even before a model is configured.

`get({roomId})` returns `{room, messages, turns, game, scene}`. `send({roomId,text,agentIds?,clientId?})` selects one to three room members in explicit order, defaulting to all three. It saves the user message and all reply placeholders together before calling models. The same client ID and identical content return the saved turn without dispatching again; conflicting reuse is rejected. Model/configuration failures reject with an Error containing `code` after persisting each speaker's state. `retry({roomId,turnId?,agentIds?})` defaults to the most recent failed/cancelled turn and only invokes members without successful replies. `cancel({roomId})` returns `{cancelled}`; `cancelAll()`, `setForeground(false)`, and `dispose()` abort the active room turn. Background/disposed services reject new sends or retries. Returning to the foreground never automatically resumes a request.

Only one room turn can run per service instance. A turn has at most three sequential model requests, each using Harness selection, its actual configured model, `system(agent,false,provider)`, the existing bounded timeout, and at most 700 output tokens. Room history never reads the private chat store. Other characters' messages are named reference data, never assistant instructions for the current character. Failures stop the remaining members; no AI reply triggers another turn. Cancellation retains partial streamed text with a cancelled status.

`play({roomId,gameId,action,agentId?,move?,guess?})` supports `rps` and `guess-number`, with `action: start|move`. RPS accepts `rock|paper|scissors` and uses a uniform local random opponent. Guessing uses an undisclosed local random integer from 1–100 with seven attempts and higher/lower feedback. Both are explicitly marked `strategy: local-rules`, run without a configured provider, and append clearly labelled local results for subsequent optional model discussion. The answer is only revealed at the end of guessing.

`scene({roomId,modelId?,objects?,interaction?})` returns `{scene,room}`. Model IDs are empty or a SHA-256 hex ID; validating the ID against owned imported assets belongs to the media bridge. No model file, texture, asset identifier, or image recognition is involved in model calls. Changing model IDs resets old object permissions and interactions. Objects have `{id,name,description,interactive,aiVisible}`, with at most 24 objects, 80 characters per name, 600 per description, and a 6,000 character annotation budget. Interactions are `{objectId,action:inspect|use|next}` and require an explicitly visible, interactive object. `next` is limited to the fictional travel itinerary, with fixed local locations and goals. The derived `scene.aiSummary` is the exact scene reference structure used in requests: only AI-visible objects and their legal interactions appear. Hidden object names and descriptions are excluded. Annotation changes are blocked while that room is generating; already submitted information cannot be retracted from a provider.

Each mutation writes a new exclusive, flushed, encrypted room snapshot in `dir/room-snapshots`; existing files are retained. Startup validates every snapshot, fails closed on corruption, and converts pending replies to failed with `RESTART`. It never contacts a model during recovery. Capacity limits are 100 rooms, 2,000 messages and 500 user turns per room. Fixtures use fresh synthetic temporary directories; the actual HTTP test connects only to loopback, never paid services or real user data.
